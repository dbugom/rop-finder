Every ID here is referenced by [REMEDIATION.md](../REMEDIATION.md). IDs are stable — do not renumber.

The audit used ROPgadget 7.7 with capstone 5.0.7 as the oracle. 32 of these findings were
re-tested by independent adversarial verifiers instructed to refute them; none were refuted.

## ECO — ecosystem gaps

### ECO-01

**No constraint-based / register-aware gadget search anywhere in the product**

- **Severity:** high  ·  **Kind:** missing-feature
- **Location:** `crates/rf-cli/src/lib.rs:41`

The only filters the CLI exposes are `--only` (mnemonic whitelist), `--filter` (mnemonic suffix suppression), `--range`, `--badbytes`, `--section` and `--cfg-aware`. There is no way to express any of the queries every peer tool supports: ropper's `--search "pop rdi; ret"` with `?`/`%` wildcards, ropper's `--semantic "rdi==..."`, angrop's `rop.set_regs(rdi=X)` (which implicitly searches for gadgets that set a register without clobbering others), or pwntools' `rop.find_gadget(['pop rdi','ret'])`. ### ECO-02

**No text-, regex-, opcode- or string-search: the CLI cannot search at all, and is behind its own MCP server**

- **Severity:** high  ·  **Kind:** missing-feature
- **Location:** `crates/rf-cli/src/lib.rs:41`

`--re` (regex over gadget text), `--align`, `--opcode` (find a byte sequence in executable segments), `--string` (find a string in readable segments) and `--memstr` are all absent from the CLI. Peers all have equivalents: rp++ `--search-hexa`/`--search-int`, ropper `--search`/`--string`/`--opcode`, radare2 `/R` + `/x` + `/`. This is doubly odd because rf-mcp *does* implement `--re` and `--align` as post-filters (crates/rf-mcp/src/lib.rs:403-405, 669-681) and lists them in its allowlist (line 55-59) — the MCP server is strictly more capable than the CLI, and `run_ropgadget_command` will therefore accept flags that `rop-finder` itself rejects. `--string`/`--memstr` are additionally refused by the MCP allowlist on security grounds, so there is no path to them anywhere in the product. Effort: `--re`/`--align` are essentially a copy of the MCP post-filter code (trivial); `--opcode`/`--string`

**Impact.** You cannot ask rop-finder where "/bin/sh" lives in a target, cannot locate a known byte pattern (`c9c3`), and cannot regex-search gadget text without piping to grep — losing the address column alignment and every JSON field. An agent that succeeded with `run_ropgadget_command --re ...` and then hands the same flag to a human teammate's `rop-finder` gets `error: unexpected argument '--re' found`.

### ECO-03

**No `--callPreceded` filter — the standard mitigation-aware gadget filter is missing**

- **Severity:** high  ·  **Kind:** missing-feature
- **Location:** `crates/rf-cli/src/lib.rs:41`

Both ROPgadget and ropper let you keep only gadgets whose entry is immediately preceded by a `call` instruction. This is not a nicety: it is the filter you need against ROP-detection policies that require every `ret` to return to a call-preceded site (EMET's caller-check, kBouncer/ROPecker-style heuristics, PaX/grsec RAP-adjacent checks), and it pairs directly with the `--cfg-aware` CET story the project already tells in UC9. rop-finder has no equivalent. Effort: LOW — the engine already does per-start linear decoding from a candidate start (crates/rf-scan/src/engine.rs); a call-preceded check is a bounded backward decode of the ≤7 bytes ending at the gadget start, and could reuse the existing decode cache. This is arguably the single best value-to-effort item after finding #1.

### CLS-03

**The `dispatcher` label (R8) fires on 99.3% non-dispatchers and misses the COP form entirely**

- **Severity:** high  ·  **Kind:** design-limitation
- **Location:** `crates/rf-classify/src/x86.rs:212-244`

R8 is internally inconsistent: for `jmp reg` it requires an earlier arithmetic step of that same register (x86.rs:227-242), but for `jmp [reg]` it requires nothing at all (x86.rs:220-225) — any register-indirect memory jump is labeled `dispatcher`. **Impact.** A user asking "which gadgets can drive a JOP chain?" gets 865 hits on bash where 6 are actually dispatcher-shaped. The label is noise at ~0.7% precision against the concept it names, and the 1224 `call [reg]`-ending gadgets that could serve as COP dispatchers are all labeled non-dispatcher.

### CLI-01

### CLI-02

**--filter is a literal suffix match, not ROPgadget's anchored regex — it both under- and over-filters**

- **Severity:** high  ·  **Kind:** parity-divergence
- **Location:** `crates/rf-scan/src/x86.rs:317-319`

ROPgadget compiles the user's --filter value into re.compile("({})$".format(value)) and applies re.match, i.e. the value is a REGEX anchored at both ends against the whole mnemonic. rop-finder splits on '|' and does `m.ends_with(s)` on each literal part. **Impact.** An analyst who runs `--filter "j.*"` believing they have removed all conditional-jump gadgets gets the complete unfiltered list back (15609 gadgets instead of 3967) and may build a chain on a gadget they intended to exclude. ### CLI-03

**--all is not implemented: no way to disable duplicate removal, costing ~13x the usable gadgets in the bad-byte workflow**

- **Severity:** high  ·  **Kind:** missing-feature
- **Location:** `crates/rf-cli/src/lib.rs:41-170`

rop-finder always deduplicates by gadget text, first-occurrence-wins (rf-scan/src/engine.rs:240-252), matching ROPgadget's default. ### CLI-04

### CHWIN-04

**The alignment invariant is anchored to a hardcoded, unstated and usually-wrong assumption about the chain base, with no way for the user to correct it**

- **Severity:** medium  ·  **Kind:** design-limitation
- **Location:** `rop-finder/crates/rf-chain/src/windows.rs:25-29 and 130-155`

The invariant's model assumes the chain base S is 16-byte aligned ("the standard exploit precondition", windows.rs:28). ## SCAN — rf-scan engine

### SCAN-01

**--filter implements neither of ROPgadget's semantics: no regex support, and suffix matching rejects gadgets ROPgadget keeps**

- **Severity:** high  ·  **Kind:** parity-divergence
- **Location:** `crates/rf-scan/src/x86.rs:317-320 (and identically cs.rs:248-251)`

ROPgadget builds `re.compile("({})$".format(re_str))` where re_str is the built-in per-arch list plus the raw user string, and applies it with `re.match` — anchored at both ends, so a plain user string is FULL-MNEMONIC EQUALITY, and a regex user string is a real regex. rop-finder instead does `m.ends_with(s)` per '|' part. Two consequences: (a) any regex metacharacter is treated literally, so the flag silently does nothing; (b) a plain string matches as a suffix, so it rejects mnemonics ROPgadget keeps ('pop'/'nop' both end in 'op'; 'iret' ends in 'ret'; 'notrack call' ends in 'call').

**Impact.** The flag either silently does nothing or silently deletes gadgets the user did not ask to remove — in both directions, with no warning. A user filtering `--filter "j.*"` to strip all jump-containing gadgets gets an unfiltered result set and may build a chain on a gadget they believed was excluded.

### SCAN-02

**Every `notrack jmp` / `notrack call` gadget is silently lost to a dedup collision**

- **Severity:** high  ·  **Kind:** correctness-bug
- **Location:** `crates/rf-scan/src/x86.rs:201-208`

capstone_normalize unconditionally strips a leading segment-name prefix ('ds ', 'cs ', ...) from any instruction with no memory operand. For a `3e`-prefixed branch capstone renders `notrack jmp`/`notrack call` (verified: capstone 5.0.7 gives `3e ff e0` -> ('notrack jmp','rax'), `3e eb e2` -> notrack jmp rel8). rop-finder's FastFormatter emits the prefix, normalize strips it, and the resulting text is byte-identical to an ordinary `jmp <target>` elsewhere in the binary — so post_process's text-keyed dedup (engine.rs:249-250) drops the notrack gadget entirely. cs_mnemonic (x86.rs:104-106) gets this right for passClean; only the text path is wrong.

**Impact.** On CET/IBT-enabled binaries the `notrack`-prefixed indirect branch is the one indirect branch that is NOT required to land on an endbr — it is the highest-value JOP primitive on such a target. rop-finder reports zero of them and gives no indication anything was dropped. This is doubly bad in a tool that ships `--cfg-aware`.
